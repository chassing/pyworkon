# pyworkon

Software development project management tool for tmux-based workflows.
Manages projects from GitHub/GitLab, organizes them in tmux sessions, and provides Textual TUI apps (dashboard + popup) plus a native macOS Dock-replacement strip (see "Strip" section below).

## Quick Reference

```bash
uv run ruff check && uv run ruff format   # lint & format
uv run mypy                                # typecheck (strict)
uv run pytest                              # tests
```

### Daemon ↔ TUI Flow

1. **Daemon** (`server.py`) runs as a background process, listens on a Unix socket
2. Daemon polls tmux sessions and PR data periodically; git branch/dirty state detected via filesystem watchers (`watchfiles`)
3. After each poll cycle or git change, daemon pushes `EVENT(state)` to all subscribers
4. Agent status updates push immediately (no polling delay)
5. **TUI apps** subscribe via `DaemonClient.subscribe()` in a background thread
6. `call_from_thread()` bridges data into Textual's main thread

**TUI is tmux-agnostic.** All tmux operations (session switching, creation, killing) go through daemon commands (`SWITCH_SESSION`, `ENTER_PROJECT`, `KILL_SESSION`). The TUI never imports `tmux_mgr` directly — the daemon is the single point of tmux interaction.

### Providers

Providers use `clientele`'s **standalone function pattern** (not class methods). Each provider exposes an async context manager via `get_provider()`.

GitHub providers support `ignored_review_requests`, a list of typed `IgnoredReviewRequests` rules with `repository` (`owner/repo`) and `authors`. The daemon filters review requests by PR author in `_fetch_review_prs_for_provider()` before caching and upstream-to-fork mapping, so TUI and relay receive the same filtered state. Repository/author matching is case-insensitive, matching rules combine their author lists, and branch PR details are unaffected. Configuration changes require a daemon restart.

## Textual TUI — CRITICAL Rules

### Widget Architecture

Widgets are fine-grained and composable. Each widget owns its own reactives, CSS (`DEFAULT_CSS`), and `update()` method:

- `SessionCard` composes `SessionHeader`, `BranchRow`, `PRDetail`, `ReviewRequestList`, `AgentList`
- `PRDetail` is independently reusable (has `show_ci_checks` parameter)
- `AgentList` is independently reusable
- `BaseApp` provides shared daemon subscription, item management, navigation
- `DashboardApp` and `PopupApp` override hooks for different behavior

### Use Reactive Properties — NEVER Manual Widget Updates

The TUI uses Textual's **reactive system** for all widget updates. This is non-negotiable.

**Pattern:**

```python
class MyWidget(Widget):
    my_text: reactive[str] = reactive("")

    def watch_my_text(self, value: str) -> None:
        with contextlib.suppress(Exception):
            self.query_one("#my-label", Label).update(value)
```

**DO:**

- Declare display data as `reactive[T]` class variables
- Implement `watch_<name>()` methods that update the DOM
- Change reactives in data-update methods → watchers handle the rest

**DO NOT:**

- Manually call `.update()` or `.remove()` on widgets outside of watchers
- Bypass the reactive system with direct DOM manipulation for data that changes over time

### Incremental Updates vs Full Rebuild

- **Structure unchanged** (same sessions, same order): update existing `SessionCard` widgets via `update_session()` → delegates to child widget `update()` methods
- **Structure changed** (session added/removed/reordered): full `_render_items()` rebuild with new `_render_generation` counter

### Widget ID Scheme

Widgets use `id=f"row-{generation}-{index}"` to avoid stale references after a rebuild.

### CSS-in-Python

All widget styles are defined as `DEFAULT_CSS` class variables, not in external `.tcss` files. Use Textual's CSS class toggling (`add_class` / `remove_class`) for state changes (e.g., `--highlight`, `--current-session`).

## Daemon

- Fully async (`asyncio`) — no `asyncio.to_thread()`, no sync blocking calls in the daemon
- JSON-Lines protocol over Unix socket
- Commands/responses defined as pydantic models in `protocol.py`
- Daemon-internal state uses `dataclasses` (`models.py`), not pydantic
- All subprocess calls go through `utils.run_cmd()` (async wrapper around `asyncio.create_subprocess_exec`)
- **Event-based push** via `SUBSCRIBE` command with event categories (`state`, `notification`). Clients specify which events they want and whether to receive initial state (`full=True`). Daemon pushes `EVENT` responses whenever state changes.
- **Git filesystem watchers** (`git_watcher.py`) using `watchfiles` — watches project root with custom filter for `.git/HEAD` (branch), `.git/index`, `.git/refs/heads/` (commit detection), and working tree files (dirty state). Branch changes detected instantly, dirty state via `git status --porcelain -uno`.
- **Circuit breaker** (`pybreaker`) per provider via `get_provider()`. After 3 consecutive API failures, the provider is paused for 5 minutes. Manual `provider sync` resets the breaker (`force=True`).
- **Tmux management** (`tmux_mgr.py`) lives in the daemon package. The daemon is the single owner of all tmux operations: session creation, switching, killing, and polling. TUI and CLI never import `tmux_mgr` directly.

### Protocol Commands

| Command             | Fields                               | Purpose                                                                |
| ------------------- | ------------------------------------ | ---------------------------------------------------------------------- |
| `OPEN_PROJECT`      | `project_id`, `pane_id?`, `session?` | Register a project as open (called by `workon` on shell entry)         |
| `CLOSE_PROJECT`     | `project_id`, `pane_id?`             | Unregister a single pane (called by `workon` on shell exit)            |
| `ENTER_PROJECT`     | `project_id`                         | Create tmux session (if needed) and switch to it (called by popup/TUI) |
| `SWITCH_SESSION`    | `session`, `pane_id?`                | Switch to an existing tmux session/pane (called by popup/TUI)          |
| `KILL_SESSION`      | `session`                            | Kill a tmux session and clean up all tracking (called by popup Ctrl-X) |
| `SUBSCRIBE`         | `events[]`, `full?`                  | Subscribe to push events (`state`, `notification`)                     |
| `AGENT_STATUS`      | `session`, `pid`, `name`, `status`   | Update agent status for a session (matched by `pid`, not `name`)       |
| `AGENT_CLEAR`       | `session`, `pid`                     | Remove an agent from a session (matched by `pid`)                      |
| `LIST_PROJECTS`     | `local?`                             | List all known projects                                                |
| `GET_PROJECT`       | `project_id`                         | Get a single project                                                   |
| `CLONE_PROJECT`     | `project_id`                         | Clone a project repository                                             |
| `SYNC_PROVIDERS`    | —                                    | Force-sync all providers                                               |
| `GET_SIDEBAR_STATE` | —                                    | One-shot state query (no subscription)                                 |
| `STATUS`            | —                                    | Daemon health/stats                                                    |
| `NOTIFY`            | `message`, `level?`                  | Broadcast a notification to subscribers                                |
| `SHUTDOWN`          | —                                    | Stop the daemon                                                        |

### CRITICAL: State Event Push Rule

**Every command that modifies `_open_projects` MUST call `_push_event("state", self._build_sidebar_state())`.** Without this, TUI subscribers (dashboard, popup) won't see the change until the next 5-second polling cycle. This was the root cause of multiple "session doesn't appear" bugs.

Commands that push state: `OPEN_PROJECT`, `CLOSE_PROJECT`, `KILL_SESSION`, `AGENT_STATUS`, `AGENT_CLEAR`, branch/dirty change callbacks.

### `AgentInfo` Identity is `pid`, Not `name`

`AgentInfo.pid` (from `_find_claude_pid()` in `interfaces/shell/commands/agent.py`) is the stable identity the daemon uses to match an existing entry in `OpenProject.agents` — `AgentInfo.name` is display-only and can legitimately change between hook calls for the *same* agent (the resolved title updates as the session's live `agent-name`/`ai-title` transcript field changes, e.g. when a delegated sub-agent starts). `_cmd_agent_status`/`_cmd_agent_clear` in `server.py` match by `pid`; matching by `name` instead caused duplicate stale entries for the same session. When updating an existing entry, update both `name` and `status` in place — never append a second `AgentInfo` for a pid that's already tracked.

### `_open_projects` Key Schema

Keys follow the pattern `{project_id}|{qualifier}`:

- `github/owner/repo|%5` — opened by `workon` with tmux pane `%5`
- `github/owner/repo|default` — opened without pane_id
- `github/owner/repo|tmux` — auto-discovered by `_poll_tmux()` or created by `ENTER_PROJECT`

The same project can have **multiple entries** (different panes/windows). `CLOSE_PROJECT` removes one entry by key. Git watcher is only unwatched when **no entries** remain for that `project_id`.

**`_cmd_open_project()`'s stale-entry collapse (the "ambiguous pane" comment in its body) must run *after* its session-resolution `await`, not before.** `_find_session_for_pane()` genuinely yields control (it shells out to `tmux` via `run_cmd()`), so two near-simultaneous `OPEN_PROJECT` calls for the same `project_id` — e.g. the default tmuxp template's "main" and "AI" windows both running their own `workon` shell hook at session startup — used to each run the stale-entry check *before* that await and could both see "no stale entry yet" in the gap, each writing their own entry. Symptom in practice: the same project showing up twice everywhere that reads `_open_projects` (two strip chips, two rows in the picker/popup) for a project that's only open in one real tmux session. Fixed by resolving the session first, then doing the stale-check-through-write as one synchronous, non-interruptible sequence — whichever call's write lands first is then correctly seen as "stale" by the other, collapsing back to one entry (`tests/test_daemon.py::test_open_project_concurrent_panes_do_not_duplicate` reproduces the race deterministically via a shared `asyncio.Event` rather than relying on `asyncio.sleep(0)` timing).

### Session Ownership (`PYWORKON_PROJECT_ID`)

Sessions created by pyworkon (via `tmuxp load`) get `PYWORKON_PROJECT_ID` as a tmux session environment variable. `KILL_SESSION` checks for this before killing — sessions without it are protected (daemon sends a warning notification instead). This prevents killing manually-created tmux sessions that happen to have `workon` running inside them.

### `_push_event` is Sync

`_push_event` uses `writer.write()` (buffer-only, no `drain()`) so it can be called from sync contexts like the circuit breaker callback (`_broadcast`). This means it doesn't await — data goes into the kernel buffer but delivery is not guaranteed before the next `await`.

## Relay (mobile web dashboard)

A read-only mobile web dashboard, fed by the daemon pushing state outbound to a small relay service (deployed separately, e.g. in a k8s cluster) rather than the phone connecting inbound to the laptop:

```text
laptop daemon --(outbound HTTPS POST, Authorization: Bearer <token>)--> relay --(WebSocket push, ?token=)--> phone browser
```

- **Daemon side** (`daemon/relay_publisher.py`): `RelayPublisher` is constructed in `Daemon.__init__` only when `config.relay_url` is set (`Config.relay_url: HttpUrl | None`, `Config.relay_token: str | None`) — fully inert otherwise. `Daemon._push_event()` calls `RelayPublisher.submit()` for every `"state"` event (not `"notification"`), which replaces any not-yet-sent payload in an `asyncio.Queue(maxsize=1)` (only the latest state matters — no backlog). A background task (`RelayPublisher.run()`) drains the queue and does a best-effort `httpx2.AsyncClient` POST to `{relay_url}/ingest`; failures/recoveries are logged only on the transition (mirrors `daemon/providers/circuit_breaker.py`'s log-spam-avoidance style), never per attempt. `to_relay_payload()` sanitizes `SidebarStatePayload` into `RelayStatePayload` — critically, it strips `Project.provider` (a `config.Provider`, which carries a `password` credential field) down to just `provider_type`, since this payload leaves the laptop.
- **Relay side** (`interfaces/relay/`): a standalone FastAPI app (`pyworkon-relay` script entrypoint), deployed independently from the daemon (see `deploy/Dockerfile`). **Must never import `pyworkon.config`, `daemon.protocol`, or `daemon.project_mgr`** — `pyworkon.config` runs `pwd.getpwnam()`/`mkdir()` at import time, which crashes under an arbitrary non-root UID (e.g. OpenShift's `restricted` SCC), which the relay container is expected to run under. `interfaces/relay/schema.py` only imports `daemon.models` (a dependency-free leaf module) for this reason — verified by `tests/test_relay_icons.py::test_importing_relay_icons_does_not_pull_in_pyworkon_config`, which must keep passing. `RelaySettings` (`interfaces/relay/config.py`) reads real env vars (`RELAY_TOKEN`/`RELAY_HOST`/`RELAY_PORT`) since the container has no `~/.config/pyworkon/config.yaml`.
- **Auth**: both the daemon's `POST /ingest` and the browser-facing `GET /` + `WS /ws` require the shared token (`secrets.compare_digest`). The daemon sends it as `Authorization: Bearer`; browsers can't set custom headers for a plain navigation or the native `WebSocket` handshake, so those two use a `?token=` query param instead.
- **Dashboard** (`interfaces/relay/static/dashboard.html`): single file, no build step, vanilla JS WebSocket client. Icons come from `interfaces/relay/icons.py`, which builds a `DASHBOARD_ICONS` dict directly from `interfaces/tui/icons.py` (stripping Rich color markup — the web page colors via CSS classes instead) and is injected into the served HTML at import time by replacing a `/*__PYWORKON_ICONS__*/` placeholder with JSON. **Never hardcode icon glyphs in `dashboard.html` — add a key to `interfaces/relay/icons.py` instead.** The PUA glyphs are served via a self-hosted webfont (`static/fonts/pyworkon-icons.woff2`) since phones essentially never have a Nerd Font installed; it's subsetted from the **Mono** variant of Nerd Fonts' "Symbols Nerd Font" release specifically because the proportional variant has wildly inconsistent per-glyph advance widths (regenerate via the command in `static/fonts/NERD_FONTS_LICENSE.txt` if a new icon is added). "Working"/pending states animate through the same Braille-dot frames Rich's `Spinner("dots", ...)` uses in the TUI, driven by one shared `setInterval` keyed off `data-spin="true"` elements.
- **Staleness**: the relay stamps `pushed_at` itself (not trusting the daemon's clock) when caching an ingest; the browser compares `Date.now()` against it every second and shows a banner past `stale_after_seconds` (`sidebar_refresh_interval * RELAY_STALE_MULTIPLIER`), mirroring the TUI's `#provider-banner` outage-banner pattern in `interfaces/tui/base.py` instead of the page just failing to load.
- **Deployment**: `deploy/Dockerfile` builds a relay-only image via `uv sync --frozen --no-dev --extra relay --no-editable` (the `relay` extra — `fastapi`/`uvicorn` — is optional so a plain CLI install doesn't pull in a web server), using the official `ghcr.io/astral-sh/uv` image (digest-pinned) rather than plain `pip`. `.github/workflows/build.yaml` builds and pushes it to `ghcr.io/<repo>-relay` on every push to `main`. k8s manifests live in a separate infra repo (not this one) — see that repo's `k3s/pyworkon-relay.yaml` for the actual `Namespace`/`Secret`/`Deployment`/`Service`/`IngressRoute` (HTTPS via the cluster's default wildcard cert, no per-route `tls:` needed).
- **PWA**: `interfaces/relay/static/pwa/` holds the manifest icons + service worker so iOS/Android can "Add to Home Screen". `GET /manifest.webmanifest` is generated per-request (not a static file) specifically so it can embed the configured token into `start_url` — otherwise relaunching from the home-screen icon would just hit the 401 gate. `GET /sw.js` is served at the root path (not `/pwa/sw.js`) so its scope covers the whole site; the worker only ever caches `/fonts/`/`/pwa/` static assets, never the dashboard page, `/ingest`, or the `/ws` connection — this is a live view that must never serve stale cached state.

## Strip (Dock-replacement bar)

`pyworkon strip` (`--auto-hide` to start collapsed) replaces the macOS Dock (set the Dock itself to auto-hide) with a thin always-on-top bar of session chips, docked at the screen bottom. Pure Python via `pywebview` (optional `strip` extra) — no HTTP server, no WebSocket, direct Unix-socket daemon subscription like the TUI. **Four separate native windows**, not one: the strip itself (chip row, never resizes except for `toggle_collapse()`); a second, dynamically-*height*-sized (fixed width) popup window for hover details that only ever resizes while hidden, then moves and shows/hides (see the "two-window" bullet below for why); a third, `focus=True` project-picker window (see `static/picker.html` below); and a fourth, right-click context-menu window (see the `show_context_menu()`/`menu.html` bullet below) that follows the same "resize only while hidden" pattern as the popup:

```text
daemon (SUBSCRIBE "state") -> background thread -> window.evaluate_js("updateState(...)") -> strip.html (WKWebView, both windows)
strip.html click/contextmenu -> pywebview.api.* -> StripBridge -> DaemonClient -> daemon
hover_monitor.py poll loop -> popup_window.evaluate_js("__showPopupFor(...)") returns measured height -> native.py (resize+position while hidden, then show/hide popup window)
```

- **Layout mode (`"full_width"` replaces the Dock entirely, auto-hiding it; `"beside_dock"` sits beside its icon area, Dock left exactly as the user has it) is a plain, user-controlled setting persisted in `config.strip_mode` (default `"full_width"`), changed only via the strip's right-click "Switch to full width"/"Switch to beside Dock" menu item (`StripBridge.toggle_mode()`, `interfaces/strip/bridge.py`).** There is deliberately **no automatic detection or re-evaluation of this setting** — an earlier design (`dock_geometry.compute_strip_layout()` auto-deciding at startup, plus `app.py` background watchers re-verifying on every `NSApplicationDidChangeScreenParametersNotification` and on an independent polling schedule) was torn out entirely after proving impossible to make reliable: confirmed via extensive live debug logging across real sleep/wake and Thunderbolt-dock monitor hotplug cycles that the Dock's own Accessibility tree and auto-hide preference could not be measured consistently enough for any retry/backoff schedule to be trustworthy — failure modes included the Dock process being transiently unqueryable for minutes after a topology change, and a `SIGKILL`-while-overridden leaving the real Dock auto-hide preference permanently poisoned with zero visible symptom to debug from. The mode now stays exactly as the user set it — through sleep, wake, monitor plug/unplug, anything — until they explicitly switch it again. `dock_geometry.compute_strip_layout(*, mode, full_width_height)` still does the one-shot placement math for whichever mode it's told to use (full_width is trivial; beside_dock measures the real Dock's position once, via Accessibility, falling back to full-width geometry for that one call if it can't).
- **`app.py`**: `start_strip()` reads `config.strip_mode`, computes that mode's layout once, and (only for `"full_width"`) enables real Dock auto-hide for its lifetime (`_set_dock_autohide()`, via `osascript`/System Events — not `defaults write && killall Dock`, which flashes), restoring whatever the user had before on exit. `recover_dock_autohide_from_unclean_shutdown()` runs first, before that first layout computation — if a previous run was `SIGKILL`'d while its override marker (`bridge.py`'s `_DOCK_AUTOHIDE_ORIGINAL_MARKER`, under `user_cache_dir`) was still on disk, it restores the *persisted* original value (not the Dock's current, possibly-still-forced setting) before anything else runs. `start_strip()` then builds the `StripBridge`, creates all **four** pywebview windows via `_build_windows()` (`frameless`, `on_top`, `transparent`; **not** `vibrancy` — see below; **`focus=False`** on every window except the picker — see below), and calls `webview.start(_listen_daemon, [window, popup_window, picker_window, menu_window, bridge, layout, height])`. `_listen_daemon` waits on all four windows' `window.events.shown.wait(15)` before touching their native frames, runs the one-time `_finalize_native_window()` (strip's style mask/collection behavior/level/initial size, popup's/picker's/menu's one-time setup, then Dock-hiding once for the whole app), then loops `DaemonClient().subscribe(["state"])`, converting each `SidebarStatePayload` via `to_strip_payload()` and pushing the same `updateState(...)` script to the strip, popup, and picker windows (the popup window needs `lastState` populated too, for `findSession()` when it's asked to render a hover; the menu window renders only explicitly-passed content via `show_context_menu()`, never daemon state, so it's never a `_push_state()` target).
- **The strip must never take focus or activate the app -- ever, not even momentarily, not even for a single click**: this is a hard product requirement, not a nice-to-have, and it's stricter than it first looks: becoming the AppKit **key window** diverts *keyboard* routing to it regardless of whether the owning app is "active" — a real click on a chip, switching tmux sessions, must leave keyboard focus in whatever terminal the user was typing into. An earlier version used `NSWindowStyleMaskNonactivatingPanel` plus a programmatic `makeKeyAndOrderFront_()` call to let exactly one click key the window (needed, at the time, to get native WKWebView hover, which requires a key window) — that directly caused a regression where *every* click keyed the window and stole keystrokes from the terminal. The actual, verified fix is `webview.create_window(..., focus=False)` for every window except the picker in `_build_windows()`: pywebview's own `WindowHost.canBecomeKeyWindow` (`webview/platforms/cocoa.py`) returns exactly that `focus` value, so `focus=False` makes a window structurally unable to become key through *any* path — our own code, pywebview's own `first_show()`/`show()`, or a real click. Ordinary clicks still reach the page fine regardless: `WKWebView` overrides `acceptsFirstMouse:` to return `YES` by default, which delivers a real click to the DOM as a normal event independent of key status — only *continuous* hover tracking (`mouseover`/`mouseout`) requires key status, which is why native hover flatly cannot be made to work focus-free. The fix for that lives in `hover_monitor.py` (see below) -- polling the mouse's global position on a background thread, with hit-testing and popup triggering done entirely on our own side.
- **Becoming "key" and the *application* activating are two separate AppKit mechanisms -- `focus=False` only fixes the first one.** Confirmed via diagnostic logging around a real click (`NSWorkspace`/`NSApplication` state captured immediately before and ~300ms after `switch_session()`): `our_window_key` correctly stayed `False`, but we became the system's frontmost process anyway. A click on any of a process's windows triggers AppKit's default "a window of mine was clicked, activate my app" behavior as standard window-server-level click routing, independent of `canBecomeKeyWindow`/`focus` -- there's no public, override-able hook for this (it isn't a call to some reachable `NSApplication` method in our own call stack; it happens at a lower level). `hover_monitor.py`'s poll loop self-corrects every tick (`_reclaim_activation_if_stolen()`), marshaled through `AppHelper.callAfter` like every other `NSApplication`/`NSWindow` mutation in this codebase (see `native.py`) -- reading simple immutable state like `NSEvent.mouseLocation()`/`window.native.frame()` from the poll thread is fine and already relied on elsewhere in this loop, but *mutating* calls need the main thread, confirmed the hard way (see below).
  - **`NSApplication.deactivate()` does not work for this process -- confirmed via diagnostic logging, not assumed.** The first version of the watchdog called `isActive()`/`deactivate()` directly from the poll thread; `isActive()` read `True` on literally every single tick, forever, for the entire session, even well before any click. Marshaling both through `AppHelper.callAfter` (matching every other AppKit mutation in this codebase) ruled out "wrong thread" as the cause -- it made zero difference, `deactivate()` still never took effect once marshaled correctly. `deactivate()` resigns active status without naming a specific app to hand it to, and apparently has nothing valid to fall back to for a never-really-foreground `NSApplicationActivationPolicyAccessory` process; macOS 14+'s "cooperative activation" changes are a documented source of exactly this kind of silently-ignored activation-state call. The fix: track whichever app was genuinely frontmost most recently (`_last_other_app`, updated every tick `NSWorkspace.frontmostApplication()` isn't us), and when we detect ourselves becoming frontmost, explicitly call `_last_other_app.activateWithOptions_(0)` -- a direct, named request that reliably takes effect where the vague `deactivate()` didn't. Confirmed working via direct user testing (click a chip while another app is genuinely frontmost; focus correctly returns to it).
- **Debugging note -- `CGEventCreateMouseEvent`-based synthetic hover simulation is not a trustworthy test oracle for this feature**: identical test code gave different results across runs, including once with `isKeyWindow`/`isActive` independently confirmed `True` via direct queries. The only test that gave a trustworthy, reproducible signal was one that explicitly activated a *different* real app (`NSWorkspace`/Finder) first, confirmed via `frontmostApplication()`/`NSApplication.isActive()` that the strip's own process was genuinely not active, *then* synthesized the mouse move and checked `frontmostApplication()` again afterward to confirm hovering didn't silently steal focus back. Don't trust a synthetic-hover test result here without that same before/after focus bookkeeping -- a test that merely launches its own script as a subprocess will itself transiently hold focus/activation purely from being launched, which silently invalidates the result. For the resize-flash investigation below, a frame-by-frame **screen recording** (the user's, captured with `Cmd+Shift+5`, inspected via `ffprobe`/`ffmpeg` frame extraction) was what finally gave a trustworthy signal, after a self-made reproduction attempt was inconclusive due to multi-monitor/crop confusion -- don't assume you can cheaply reproduce a visual artifact yourself; ask for a recording rather than guessing from a fourth code change.
- **`vibrancy=False`, not `True`**: the original `vibrancy=True` (an `NSVisualEffectView` blurring the desktop behind the window) produced a flat gray/white panel covering everything above the strip whenever the hover popup grew the window taller, instead of a blur. CSS `rgba(...)` backgrounds on `#strip`/`#popup` already give enough of a translucent look without it, and removing it entirely sidesteps whatever interaction this had with the window's non-key/background state. Applies to both windows.
- **Quitting**: the strip is frameless with no Dock icon tile interaction, menu bar, or close button, so `StripBridge.quit()` (wired to the "Quit strip" item on the right-click-on-empty-space context menu, alongside the mode-switch item above) destroying **all four** windows is the *only* clean way to stop it -- `webview.start()` only returns once every window it created has closed, so leaving any of them open after destroying just the strip would hang the process. This matters because `start_strip()`'s Dock-auto-hide restore lives in a `finally` around `webview.start()` — a `kill`/`pkill`/SIGTERM cannot reach that `finally` because the main thread is blocked inside AppKit's native run loop and never gets a chance to run pending Python-level signal handlers (confirmed empirically: a `SIGTERM` handler calling `sys.exit()` from a bare pywebview app doesn't fire reliably, or fires without unwinding the stack). `window.destroy()` is different — it's pywebview's own clean-shutdown path and reliably makes `webview.start()` return normally once *all* windows are destroyed. **But that alone isn't enough to actually quit the process**: `webview.start(func, args)` spawns `func` (`_listen_daemon`, with its `while True` daemon-subscribe loop) as a plain, non-`daemon=True` `threading.Thread` -- pywebview's own thread creation, outside our control. Once `webview.start()` returns, that thread is still looping forever, and the interpreter won't exit while any non-daemon thread is alive — "Quit strip" would otherwise close the windows but leave the process running invisibly. `start_strip()` ends with `os._exit(0)` (after the Dock-restore `finally`) to force real termination; confirmed by reproducing the hang with a toy infinite-loop thread standing in for `_listen_daemon`, then confirming `os._exit(0)` fixes it the same way.
- **Critical ordering gotcha**: `webview.start(func, args)` starts the `func` background thread **before** calling `guilib.create_window()` on the main thread — none of the windows may exist or be shown yet when the thread starts. Any native-window mutation done without waiting for `window.events.shown` first races pywebview's own initial setup and gets silently clobbered (the window ends up positioned wherever pywebview's defaults put it, not where you asked). This cost real debugging time — don't skip the `shown.wait()` for **any** window.
- **`native.py`** is split into **one-time** setup functions (`prepare_window()`/`prepare_popup_window()`/`prepare_picker_window()`/`prepare_menu_window()`/`hide_from_dock()`) and **repeatable** mutation functions (`resize_frame()` for the strip; `resize_and_position_popup_window()`/`show_popup_window()`/`hide_popup_window()` for the popup; `resize_and_position_menu_window()`/`show_menu_window()`/`hide_menu_window()` for the context menu) — do not merge them back together:
  - `prepare_window()` (called exactly once, from `_finalize_native_window()`): sets the strip's native `NSWindow`'s style mask to plain `NSWindowStyleMaskBorderless` (value `0`). This fixes pywebview's own `Window.move()`/`.resize()` going through AppKit's `constrainFrameRect:toScreen:`, which refuses to let a **titled** window (pywebview's `frameless=True` still carries `NSWindowStyleMaskTitled` — the titlebar is just visually hidden) sit fully flush with the screen edge -- any borderless-family mask disables that. An earlier version added `NSWindowStyleMaskNonactivatingPanel` on top specifically so a real click could key the window without activating the app (for native hover) — that bit is gone now: the window must never become key *at all* (see the "must never take focus" bullet above), which `app.py`'s `focus=False` already guarantees on its own, so no style-mask trick is needed for it. Also sets the collection behavior (`CanJoinAllSpaces | Stationary`, so the strip follows across every macOS Space like the real Dock), the window **level to 19** — one below the real Dock's own CG window layer (20, confirmed via `Quartz.CGWindowListCopyWindowInfo`) so the strip stays above ordinary app windows (Terminal/browser/editor sit at `NSNormalWindowLevel`=0) but still *yields to the real Dock* when the user hovers the screen edge to reveal it (`NSStatusWindowLevel`, 25, pywebview's own `on_top=True` default, is *above* the Dock and was the original bug), and `setAcceptsMouseMovedEvents_` (harmless to leave set even though hover is ultimately driven by `hover_monitor.py`, not native tracking). Calls `orderFrontRegardless()`, not `makeKeyAndOrderFront_()` — shows the window without even attempting to key it.
  - `resize_frame()` (called on every `toggle_collapse()`, strip window only -- the popup window never resizes at all, see below): only touches `setFrame_display_`, never the style mask again. An earlier version called the equivalent of `prepare_window()` on every resize; re-applying `setStyleMask_` resets the WKWebView's transparent-background flag that pywebview configures once at window-creation time, which made the window flash an opaque gray/white fill the first time it grew taller. Verified via `Quartz.CGWindowListCreateImage` pixel sampling: re-touching the style mask on resize → alpha a solid value; leaving it alone after the first `prepare_window()` call → alpha 0 (transparent) in the newly-exposed area, every time. Passes `display=True` to `setFrame_display_` -- an attempt switched this to `display=False` as a best-effort mitigation for a one-frame blank flash during resize (back when the popup still grew the strip's own window, see below), and it was **reverted**: diagnostic logging showed deferring the redisplay also appears to defer the WKWebView's own internal relayout (and therefore its JS-visible `resize` event, and therefore `reportChipRects()`'s report of each chip's new on-screen position), while `native.frame()` reflects the new size immediately regardless of the `display` flag -- that reopened a stale-chip-rect race, confirmed via logging showing the *same* chip's hover state flapping open/closed repeatedly.
  - `prepare_popup_window()` (called exactly once, for the popup window): same style mask/collection-behavior/level setup as `prepare_window()`, but **starts hidden** via `orderOut_()` (never `orderFrontRegardless()`) -- it should only become visible when a chip is actually hovered.
  - `resize_and_position_popup_window(native, x, y, width, height)` / `show_popup_window(native)` / `hide_popup_window(native)`: the popup window's three mutations, called from `hover_monitor.py`, always in that order for showing it (resize **while still hidden**, then show). `resize_and_position_popup_window()` *does* resize (unlike the strip window's dedicated "never resize" guarantee) -- for dynamic height, see `clamp_popup_height()`/`POPUP_MIN_HEIGHT`/`POPUP_MAX_HEIGHT` below -- but this is safe precisely because it's never called on a window the user can already see: `show_popup_window()` (`orderFrontRegardless()`) is a deliberately separate, later call. This is the fix for the resize-flash bug below -- a window that's resized only while invisible can't exhibit a visible flash.
  - `hide_from_dock()` (called exactly once, **after** every window's one-time setup): switches `NSApplication` to `NSApplicationActivationPolicyAccessory`, which drops the Dock tile and Cmd+Tab entry entirely — a bundle-less Python process otherwise shows up with the interpreter's own name/generic icon (`python3.15` in the Dock tooltip), and there's no reliable bundle-less way to make that look like a real app icon. Ordering matters here too: back when the window still briefly became key on creation (before `focus=False` made that impossible outright), switching to Accessory *before* that happened left it permanently unable to receive hover events, even though `canBecomeKeyWindow` still reported `True` — confirmed by swapping the two calls and re-running the hover test. Hover no longer depends on key-window status at all (see `hover_monitor.py`), but this ordering is kept as-is since it's already verified safe.
  - AppKit requires window mutation on the **main thread**; every function above marshals through `PyObjCTools.AppHelper.callAfter` — calling `NSWindow`/`NSApplication` selectors directly from `webview.start()`'s background thread can crash the process outright (an Objective-C "unrecognized selector"-style failure, not a catchable Python exception). Tests stub this out via an autouse fixture that monkeypatches `AppHelper.callAfter` to run synchronously (there's no Cocoa run loop pumping in plain pytest).
- **The hover-detail popup is a *separate window* with a fixed width but dynamic height (`POPUP_WIDTH` 360, clamped between `POPUP_MIN_HEIGHT` 100 and `POPUP_MAX_HEIGHT` 480), not part of the strip's own resizable frame.** This was a significant redesign, not the original architecture -- the original approach grew the *strip's own* window taller (to a fixed `EXPANDED_HEIGHT`) to make room for the popup, with `#popup` CSS-positioned above the chip row within that one page. **Confirmed via a frame-by-frame screen recording** (not assumed) that this made the window briefly, fully transparent -- the desktop wallpaper visibly showed through for ~2 frames (~33ms) -- during the native resize, consistent with WKWebView's own rendering being asynchronous and out-of-process from the window itself, something no amount of synchronous `display:`/alpha/CSS tricks on the *window* side could reliably wait for. **Three independent fix attempts at masking this were all tried and reverted, each confirmed (by direct user report) to make it *worse*, not better:** (1) `display=False` on the native resize -- broke `reportChipRects()` timing, reopening a functional stale-rect jitter bug; (2) an alpha dip (hide/resize/reveal) around the native resize -- caused a visible flicker on *every* resize (open and close), worse than the original single-direction flash; (3) CSS GPU-layer promotion on `#strip` (`transform: translateZ(0); backface-visibility: hidden;`) -- also made it worse. Giving the popup its own window sidesteps the problem at the source instead of trying to mask it: it only ever resizes **while still hidden** (see `_process()` below), so there's never a visible frame for WKWebView's relayout lag to race against -- unlike the strip window, which genuinely never resizes at all except for `toggle_collapse()`. The trade-off, explicitly accepted by the user after an earlier "always keep the strip window tall" alternative was rejected (that one really would have intercepted clicks meant for whatever's behind the strip near the screen's bottom edge, which was correctly vetoed): the popup window is a second window to keep synchronized (both receive `updateState()`; `StripBridge`/`HoverMonitor` are shared between them via the same `js_api`).
- **`hover_monitor.py`** (`HoverMonitor`) is what actually makes the hover popup work while the strip has no focus -- see the "must never take focus" bullet above for why native WKWebView hover can't do this. Takes **both** windows (`HoverMonitor(window, popup_window)`). Architecture:
  - A background thread (`_poll_loop()`) polls `AppKit.NSEvent.mouseLocation()` (current global cursor position) every 30ms (`_POLL_INTERVAL_SECONDS`) and does cheap point-in-rect hit-testing against the chip rectangles `strip.html` reports after each render (`update_chip_rects()`, via the `StripBridge` method of the same name). An earlier version used an `NSEvent` **global event monitor** (`addGlobalMonitorForEventsMatchingMask:handler:`) instead of polling — that requires Accessibility permission (System Settings > Privacy & Security > Accessibility) and, worse, was empirically *unreliable*: hover sometimes fired instantly, sometimes only after a multi-second delay, and sometimes not at all until the mouse moved onto a different chip (consistent with macOS's App Nap throttling a never-active `NSApplicationActivationPolicyAccessory` process's run loop, or with flaky TCC permission bookkeeping across relaunches). Plain `mouseLocation()` polling needs **no special permission at all** (confirmed against real-world precedent — e.g. the `sketchybar-toggle` macOS utility polls it at 60Hz from a background daemon with zero entitlements) and removes the entire "was this event actually delivered, and when" class of uncertainty: every tick is a fresh, synchronous read of where the cursor actually is right now.
  - **No separate consumer thread needed**: since `_poll_loop()` already runs on its own dedicated background thread (never AppKit's main thread), it's safe to call the blocking `evaluate_js()` directly from `_poll_once()`/`_process()` — unlike a main-thread-delivered global-monitor callback (which would deadlock, since `evaluate_js()` itself needs the main thread's run loop to complete), there's no risk here. The loop wraps each tick in `contextlib.suppress(Exception)` — an uncaught exception would otherwise silently kill the thread forever (no more hover for the rest of the process's life, with no visible error), and `evaluate_js()` reaching into a WKWebView that's mid-resize or mid-navigation is exactly the kind of best-effort call that can occasionally fail transiently.
  - **The popup window's own on-screen rect is checked directly via its native frame (`_mouse_over_popup_window()`), not a CSS-reported rect from `strip.html`.** Since *we* set the popup window's position, there's no need for `strip.html` to report it back the way the old single-window design needed `update_popup_rect()` to -- that bridge method and `set_popup_rect()` are gone entirely. `native.isVisible()` is checked too, so a hidden-but-still-positioned-somewhere popup window never spuriously counts as "mouse is over it."
  - Hitting a chip's rect calls `_process(session_name)`, in strict order: (1) `popup_window.evaluate_js("window.__showPopupFor(...)")` -- blocks until the script actually runs, rendering content into `#popup` and **returning the measured `scrollHeight`** as the expression's value, which `evaluate_js()` hands straight back to Python; (2) `clamp_popup_height()` that value into `[POPUP_MIN_HEIGHT, POPUP_MAX_HEIGHT]`; (3) `resize_and_position_popup_window()` to that height, while the window is **still hidden**; (4) only then `show_popup_window()`. Reordering any of these risks either a flash of stale content/size (show before resize/render) or the (now reintroduced, since the popup *does* resize) WKWebView-relayout flash (resize while already visible). Hitting nothing calls `_process(None)`, which just hides the popup window (`hide_popup_window()`). Hitting the currently-open popup window's own frame returns `_KEEP_CURRENT` from `_hit_test()` -- treated as "stay open," changing neither `_hovered` nor triggering any call.
  - `_popup_screen_position(session_name)`: computes the popup window's target origin (AppKit bottom-left coordinates) from the hovered chip's rect plus the strip window's own frame -- `y` is always the strip window's top edge (`strip_frame.origin.y + strip_frame.size.height`, since the popup always sits just above the chip row); `x` is anchored to the chip's left edge, clamped by `_SCREEN_EDGE_MARGIN` (8px, mirroring the old CSS clamp) so the fixed-width popup never runs off either side of the screen.
  - **`_HIT_MARGIN` (4px tolerance on every chip rect)** is a secondary mitigation for ordinary sub-pixel mouse jitter at an edge; it did **not** fix the main jitter bug by itself (see below).
  - **The actual, confirmed-via-logging cause of the whole strip jittering non-stop once a popup opened (back when the popup still grew the strip's own window)**: `#strip` in `strip.html` is CSS-pinned to `bottom: 0`, so a chip's on-screen position shifted every time the native window resized (56px ↔ 376px) even though nothing re-rendered. `reportChipRects()` was only called from `renderStrip()` (on daemon state pushes) -- *not* after a resize -- so the hover monitor's cached chip rects went stale the instant the window's height changed: read against the new viewport height, a stale rect reads as "mouse left the chip," closing the popup and shrinking the window back down, which makes the stale rect correct again, reading as "mouse is back on the chip" -- reopening it, forever. Diagnostic logging showed this exact alternation repeating every ~150ms nonstop. This whole class of bug is now structurally impossible -- the strip window no longer resizes for hover at all (see the "separate window" bullet above), so its chips' on-screen positions never shift from this.
  - **Residual, isolated jitter observed even after that fix** (an occasional single flap-shut-and-reopen, not a sustained loop; this was back when the popup still grew the strip's own window, but the debounce itself is a generally-useful hardening against transient misses regardless): `_poll_once()` debounces the *leave* transition specifically -- `_LEAVE_DEBOUNCE_TICKS` (3, ~90ms at the 30ms poll interval) consecutive misses are required before committing to "left," via a `_miss_streak` counter reset on any hit (including `_KEEP_CURRENT`). A single transient miss (residual mouse micro-jitter, or a chip's rect shifting for exactly one tick while a daemon-pushed re-render reflows the row) no longer closes the popup immediately. Switching directly between two *different* chips is never debounced -- only `target is None` increments the streak.
- **`bridge.py`** (`StripBridge`): the `js_api` object pywebview exposes to **both** windows as `pywebview.api.*` (the same bridge instance is passed to both `create_window()` calls). `bind(window, popup_window, *, screen, collapsed)` constructs and starts the shared `HoverMonitor`. `update_chip_rects()` forwards straight to it (`update_popup_rect()` is gone -- see `hover_monitor.py` above). `switch_session`/`kill_session` mirror `interfaces/tui/base.py`'s `BaseApp` static methods (duplicated, not imported — the strip has no Textual dependency); `kill_session` has no JS-side `confirm()` dialog — the context menu's "Kill session" item is itself the confirmation, a second dialog on top would just be an extra click. `toggle_collapse()` resizes the *strip window only* between `STRIP_HEIGHT` (56) and `COLLAPSED_HEIGHT` (10), and also hides the popup window (`hide_popup_window()`) -- collapsing mid-hover shouldn't leave the popup floating above a now-hidden strip. `quit()` destroys **both** windows (see the "Quitting" bullet above for why that's required, not optional).
- **`schema.py`** (`to_strip_payload()`): sanitizes `SidebarStatePayload` the same way `daemon/relay_publisher.to_relay_payload()` does — strips `Project.provider`'s credential field down to `provider_type` — even though the strip's JS never leaves the machine, because the WebView's JS context still has no legitimate reason to see it. Also flattens the daemon's `review_prs: dict[str, list[ReviewPR]]` onto each matching session by `project_id` so the hover popup can render them without a second lookup.
- **`static/strip.html`**: single file, no build step, **shared by both windows** -- `app.py`'s `_render_strip_html(is_popup: bool)` substitutes a `__PYWORKON_IS_POPUP__` placeholder into `const IS_POPUP_WINDOW = true/false;` near the top of the script, and a `body.popup-window` class (set from that constant) gates the CSS between the two modes. Horizontal flexbox chip row (`#strip`, plain tmux sessions rendered first, then project sessions) shows only the essentials per session: a CI/agent-derived "attention level" (`chipAttentionLevel()` — a failed CI check *or* an agent in `waiting` status both count as needing attention and turn the chip red; a pending CI check or a `working` agent turns it yellow; otherwise no extra badge at all, deliberately no "OK" badge) and a dedicated full-chip-height `.chip-agent` column (not an inline badge) for the agent status icon/spinner, since that needed to read clearly at a glance. That same column also renders the `reviewRequest` eye icon (`renderChipStatus()`, `.chip-status.status-review`) whenever `session.review_prs` is non-empty, but only once every higher-priority state (agent waiting, agent working/CI pending, CI failed) has already been ruled out — an open review request never competes with or overrides a real "come look at this" signal, it only surfaces once the chip would otherwise show nothing or just the dim idle icon. The hover popup's "Review requests" block (`renderReviewRequests()`) uses the same `.section`/`.section-heading`/`.section-label` markup as Branch/Pull Request/Checks/AI (count shown via `.section-context`, e.g. "1 review", with the author rendered as a labeled, non-shrinking `by <author>` on the row's right) rather than a bespoke `.reviews-block` header with an inline icon and a "(N)" suffix baked into the label text — that older pattern was the one section visually inconsistent with the rest of the popup. All popup links (`.pr-link`, `.review-title`) share one color and are never underlined, and the PR-state pill renders only for states that deviate from open (`closed`/`merged`) — an "Open pull request" pill only repeated the default and collided visually with "Approved". A draft is one more pill in that same review line rather than an early return, so a draft that was closed still reads `Draft pull request · Closed pull request` (neither GitHub nor GitLab lets a draft be merged, so `Merged` only ever pairs with a non-draft); the title itself carries no `[Draft] ` prefix, since the faded `.pr-title.draft` plus that pill already say it.
  - **Strip-window mode** (`IS_POPUP_WINDOW === false`): `#strip` renders normally; `#popup`/`#handle`/`#ctxmenu` behave as before (CSS-hidden by default, shown by their own class toggles). `updateState()`/`reportChipRects()` run normally.
  - **Popup-window mode** (`IS_POPUP_WINDOW === true`): `body.popup-window` CSS forces `#strip`/`#handle`/`#ctxmenu` to `display: none !important` and makes `#popup` fill the entire (separate, fixed-size) window (`width: 100%; height: 100%; max-height: 100vh`, since the base rule no longer carries any sizing at all). `updateState()` still updates `lastState` (needed for `findSession()`) but **returns early, never calling `renderStrip()`** -- and `reportChipRects()` itself also independently checks `IS_POPUP_WINDOW` as a second guard. This matters: both windows share the *same* `HoverMonitor` instance via the same `js_api` bridge, so if the popup window's `#strip` (which would just be empty/hidden, never populated) ever got rect-reported, it would overwrite the real chip rects with an empty list and silently break hover entirely. The `window.addEventListener("resize", ...)` handler (collapse-class + rect refresh) is skipped entirely in popup-window mode too, for the same reason -- the popup window's size never changes anyway (see `native.py` above).
  - `window.__showPopupFor(sessionName)` is the only hover-related entry point now (replacing the old single-window design's `window.__hoverEnter`/`__hoverLeave`, which used to manage the strip's own `#popup` div in place). Called only on the popup window (via `hover_monitor.py`'s `evaluate_js()`); looks up the session in `lastState` -- **or**, if it's a plain tmux session (present in `lastState.plain_sessions`, which is just a list of names, not `lastState.sessions`), renders a minimal `renderPlainPopupContent()` instead (just the name) rather than silently showing nothing, which is what a plain session's hover used to do before this fix. Either way, **returns `Math.ceil(popup.scrollHeight)`** as the function's value -- this is what `hover_monitor.py`'s `_process()` uses to size the (still-hidden) native window; `scrollHeight` reports the full content height regardless of `#popup`'s current, likely-stale-from-the-previous-hover size, since it can already overflow its visible area (`overflow-y: auto` on the base `#popup` rule). Positioning/sizing and show/hide are otherwise handled entirely natively from Python (`native.py`'s `resize_and_position_popup_window()`/`show_popup_window()`/`hide_popup_window()`).
  - `[data-url] { cursor: pointer; }` is a single, universal rule covering every clickable link in the popup -- added after a successful (not just pending/failed) CI check with a url was found clickable but showing the default arrow cursor, since only `.ci-check-failure` (not `.ci-check-success`/`.ci-check-pending`) had its own `cursor: pointer`. Add future clickable elements with a `data-url` attribute (matching the delegated click handler's own `ev.target.closest("[data-url]")` selector) rather than remembering to add `cursor: pointer` to each new status-specific class individually.
  - **Click (and right-click, and the popup's own link clicks) are still native DOM events** — and this is the *primary* mechanism, not a fallback: since neither window can ever become key (`focus=False`, see above), the only thing that was ever gated on key status was continuous hover tracking. `WKWebView` overrides `acceptsFirstMouse:` to return `YES` by default, so ordinary clicks are delivered to the DOM as normal events regardless of key status. The delegated native `click`/`contextmenu` listeners on `#strip` are bound **once**, not per-chip inside `renderStrip()`, for the same reason per-chip listeners would be fragile (a per-chip listener dies with the old DOM node on every re-render). There is deliberately **no native `mouseover`/`mouseout` listener on `#strip`, nor `mouseenter`/`mouseleave` on `#popup`** anymore — a background, never-key window's WKWebView never receives those at all, so they would be permanently dead code.
  - Links inside the popup are `data-url` spans with a single delegated click handler calling `pywebview.api.open_url()` — plain `<a href target="_blank">` would try to open a second WKWebView window instead of the user's real browser. The Nerd Font webfont is embedded as a base64 `data:` URI (`_render_strip_html()` injects it via a `__PYWORKON_FONT_BASE64__` placeholder, reusing `relay/static/fonts/pyworkon-icons.woff2` through `importlib.resources` — no separate font asset for the strip) since there's no static file server to serve it from the way the relay does.
  - Right-click on empty strip background shows a two-item menu: the mode-switch toggle (its label names the *target* mode, e.g. "Switch to beside Dock", read from whether `body` currently has the `beside-dock` class) and "Quit strip" — a now-removed "Collapse strip" item made the menu wider than needed and wasn't being used (mini-mode is reached via `--auto-hide` at startup, or by clicking the collapsed-state `#handle`, whose `toggle_collapse()` call is unrelated to this menu).
- **`hotkey.py`**: a system-wide macOS hotkey (`Config.strip_hotkey`, default `ctrl+option+space`) toggles the project picker from any app, via `StripBridge.toggle_project_picker()` — the same window `open_project_picker()`/`close_project_picker()` already manage, no new window. `NSEvent.addGlobalMonitorForEventsMatchingMask:` was ruled out before writing any code: Apple's own docs confirm it only receives key events once the app has Accessibility permission, and a `CGEventTap` needs Input Monitoring instead — neither is acceptable for a background utility with no onboarding flow. Carbon's `RegisterEventHotKey`/`InstallEventHandler` need **no permission at all** (a narrowly-scoped "notify me on this exact combo" registration, unlike a monitor/tap that can observe arbitrary input) and remain present in the OS despite Carbon itself being deprecated — but PyObjC no longer ships bindings for them.
  - `_load_hitoolbox()` bridges the needed subset directly via `objc.createFrameworkDirAndGetattr()`, pointed at `/System/Library/Frameworks/Carbon.framework/Versions/Current/Frameworks/HIToolbox.framework`. The C function-signature/struct-type byte strings passed as `metadict` are ported **verbatim**, not hand-derived, from the MIT-licensed `QuickMacHotKey` project (https://github.com/glyph/QuickMacHotKey, Copyright (c) 2023 Glyph Lefkowitz) — getting one byte of a C type encoding wrong here risks a native crash, not a catchable Python exception, so this reuses a verified-working reference rather than guessing at the Carbon Event Manager's ABI. `register_hotkey()`/`parse_hotkey()` and the `_HotkeyRegistry` class around them are pyworkon's own code; only the bridging metadata inside `_load_hitoolbox()` is ported.
  - **`metadict["misc"]` resolves eagerly, `metadict["functions"]`/`["enums"]` resolve lazily — confirmed by reading `objc/_lazyimport.py`'s source, not assumed.** `createFrameworkDirAndGetattr()` does `globals_dict.update(metadict.get("misc", {}))` immediately, so `EventTypeSpec` (a struct type registered via `objc.createStructType()`) is already sitting in the returned namespace the moment the call returns. Functions and enum constants are *not* — they're resolved on demand through the returned `getattr_func()`, which checks `funcmap`/`enummap` internally. The first version of `_load_hitoolbox()` called `getattr_func("EventTypeSpec")` for everything uniformly and got `AttributeError: EventTypeSpec`, since `__getattr__`'s lookup path (constants → classes) never consults `globals_dict` for names already placed there by the `misc` merge. Fixed by reading `misc`-sourced names directly out of the namespace dict and reserving `getattr_func()` calls for `functions`/`enums` names only.
  - Verified working by direct testing on a real Mac (not just type-checked): loading the bridge and doing a real `RegisterEventHotKey`/`InstallEventHandler`/`UnregisterEventHotKey` round-trip outside pywebview's run loop returns OSStatus `0` (`noErr`) at every step, including through the `@objc.callbackFor`-decorated event callback.
  - Only one hotkey is ever registered (fixed signature `b"PYWK"`, id `1`) — `_HotkeyRegistry` exists as a class instead of module-level globals specifically because ruff's `PLW0603` (`global-statement`) flags mutating module globals via `global`, and per this repo's linter-suppression rule that's a reason to restructure the code, not silence the rule; it mirrors `StripBridge`/`HoverMonitor`'s own "encapsulate mutable state in a class" pattern.
  - `RegisterEventHotKey`/`InstallEventHandler` must run on the main thread, same as every other AppKit-touching call in this package (see `native.py`'s module docstring) — `register_hotkey()` marshals both through `AppHelper.callAfter`. The fired hotkey event callback itself also arrives on the main thread; it hands off to a new background `threading.Thread` before invoking the registered callback (`StripBridge.toggle_project_picker`), mirroring `native.py`'s `prepare_picker_window()`/`_handle_resign_key` pattern exactly — `toggle_project_picker()` can reach `Window.evaluate_js()` (`AppHelper.callAfter(eval); semaphore.acquire()`), and calling that synchronously from the main thread would deadlock the same way that pattern already documents.
  - `app.py`'s `_listen_daemon()` registers the hotkey (if `config.strip_hotkey` is non-empty), wrapped in `contextlib.suppress(Exception)` — a malformed `strip_hotkey` config value must not take down this whole background thread, which also runs the daemon-subscribe loop below it. `parse_hotkey()` requires at least one modifier, rejecting a bare key like `"space"` that would otherwise globally intercept every press of that key system-wide.
  - `pyproject.toml`'s `[[tool.mypy.overrides]]` gained an `"objc"` entry alongside the existing `"AppKit"`/`"PyObjCTools.*"` ones — `hotkey.py` is the first file in this codebase to `import objc` directly rather than only `AppKit`/`PyObjCTools`.
- **`static/picker.html`** renders two different views of the same daemon state, chosen per-invocation by `bridge.py`'s `open_project_picker(*, switcher_mode: bool = False)` and forwarded to the page via `__onPickerShown(switcher)` (a module-level JS `switcherMode` variable, read by every subsequent `render()` call until the picker is shown again):
  - **Button mode** (`switcher_mode=False`, the "+" chip's default, unchanged call site) stays project-centric: `buildButtonModeItems()` merges `state.sessions` (open project-sessions) and `state.projects` (closed projects) into **one list, sorted alphabetically** by display name (`localeCompare`, case-insensitive) — no reordering, no plain tmux sessions (they aren't "projects").
  - **Switcher mode** (`switcher_mode=True`, `toggle_project_picker()`'s hotkey callback) turns the same window into a universal switcher: `buildSwitcherModeItems()` builds `open = [*plain_sessions, *sessions]` and `closed = [*projects]`, in the daemon's own pre-sorted order (not re-sorted again) — matching `interfaces/tui/base.py`'s `BaseApp._render_items()` section order (`[*plain, *sessions, *projects]`) exactly, since this view's whole purpose is parity with the old Textual popup. A `.section-divider` renders between the two groups only when both are non-empty.
  - **Every row for a currently-open item (plain or session, in *either* mode) gets a `.badge-open` "Open" pill**, right-aligned via the row's existing flexbox + `.project-copy`'s `flex: 1`. An earlier version only showed this badge in button mode (reasoning that switcher mode's grouping already communicates "open") — reverted after direct user feedback that the badge should render in both modes regardless of the grouping.
  - Both modes filter each bucket independently via `matchesTerm()` (plain sessions match on name only; sessions/projects match on `"{project_name} {owner}"`) before concatenating `[...openMatches, ...closedMatches]` into `currentMatches` — filtering can never move an item across the open/closed boundary.
  - `activateItem()` (renamed from the old `openProject()`) branches on the normalized item's `kind`: `"project"` → `pywebview.api.enter_project(project_id)` (unchanged); `"session"`/`"plain"` → the new `StripBridge.switch_session_from_picker(session_name)` (`bridge.py`), which calls `close_project_picker()` then `switch_session()` — mirroring `enter_project()`'s "close the picker before the call" ordering. `switch_session()` itself is untouched, since strip chip clicks call it directly with no picker involved.
  - `killItem()`, bound to `Ctrl+X` in the same `keydown` listener as Escape/arrows/Enter, mirrors `interfaces/tui/base.py`'s `BaseApp.action_kill_session()`: no JS `confirm()` dialog (pressing the key is itself the confirmation, same reasoning as the strip chip's own context-menu kill item), a no-op for a closed project (nothing running to kill), and the picker stays open afterward — the killed session just drops out of the list on the next daemon state push, same as the TUI popup never exiting on kill either. Calls the existing `StripBridge.kill_session()` (no new bridge method needed). `ev.preventDefault()` here is load-bearing, not tidy: Ctrl+X is the native "cut" shortcut for a focused text input, and `#filter` always has focus while the picker is open.
  - Plain-session rows get a proper icon (`ICONS.plainSession`) instead of a bare hardcoded glyph — `"plainSession": tui_icons.ICON_PLAIN_SESSION` (the same `▸` the TUI already uses for plain tmux sessions) was added to `DASHBOARD_ICONS` in `interfaces/relay/icons.py` for this, per this file family's "never hardcode icon glyphs in HTML, add a key to relay/icons.py instead" rule (see the relay dashboard section below). `▸` (U+25B8, plain Unicode, not a Nerd Font PUA glyph) has far more built-in whitespace around its "ink" than the Nerd Font provider glyphs at the same font-size and renders distractingly small/colorless next to them — `.provider.plain` bumps it to `font-size: 28px` and gives it its own color (`#7aa2e0`) rather than inheriting `.provider`'s default gray, confirmed by rendering the real `_render_picker_html()` output (actual embedded font/icons, not a stand-in) in a real browser and visually comparing row heights/weights side by side, not by guessing pixel values blindly. The search-row's own magnifier icon (`⌕`, also plain Unicode with the same built-in-whitespace issue) needed the same treatment — settled at `font-size: 24px` after the same screenshot-based comparison (34px was tried and confirmed too big by the user, who had been looking at the running app directly).
  - `state.sessions`/`state.projects` are mutually exclusive by construction — confirmed by reading `daemon/server.py`'s `_build_sidebar_state()`, whose `projects` list comprehension explicitly excludes any project id present in `_open_projects` (the same dict `sessions` is built from, in the same synchronous, non-`await`-ing call) — so button mode's merge can never produce a duplicate row for the same project. This invariant is why a *different*, real duplicate-row bug (see `daemon/server.py`'s `_cmd_open_project()` below) was a backend data problem, not a picker rendering problem, even though it was first reported as "I see the same project twice in the picker and as two strip chips."
  - Verified against realistic mixed open/closed/plain state by extracting the `<script>` block, stubbing `document`/`pywebview` in plain Node, and asserting the rendered order, filtering behavior, and exact `pywebview.api.*` calls dispatched per item kind in both modes — not just type/syntax-checked.

## CLI

- Uses **Click** (not typer) — the CLI is Click-based
- Subcommands auto-discovered from `interfaces/shell/commands/`
- `app.py` installs the standalone macOS Dashboard wrapper with a nested `Contents/Resources/Pyworkon Terminal.app` runtime copied from `/Applications/Ghostty.app` using `ditto --noqtn`. The wrapper exports its private `XDG_CONFIG_HOME` before opening the nested native bundle through `/usr/bin/open -na ...`. The runtime's `LSEnvironment.XDG_CONFIG_HOME` points to `Contents/Resources/ghostty-config` in the final installed bundle, not the staging directory, so direct launches from a pinned Dock icon also load the dashboard configuration. The private bootstrap includes the original XDG Ghostty configuration and then `ghostty.conf`; Ghostty still loads its normal macOS configuration natively. Do not include that macOS configuration a second time: nested `config-file` entries would produce cycle diagnostics. The dashboard command uses `/usr/bin/env` to restore the original `XDG_CONFIG_HOME`, including unsetting it when originally absent. Keep `CFBundleExecutable` as the original native `ghostty`: launcher shims can invalidate the application PID reported to accessibility/window managers such as Rectangle. The runtime uses `dev.pyworkon.dashboard.terminal` and the bundled `PyworkonDashboard.icns`; its `CFBundleIconName` and `NSDockTilePlugIn` overrides are removed. Do not use Ghostty's `macos-icon` custom settings: its Dock plugin shares icon preferences across instances. Only the copy is ad-hoc signed (preserving entitlements) and verified. Installation builds in a temporary sibling directory before replacing the old app, with rollback on publication failure. The Dashboard config disables runtime auto-updates. Close the Dashboard and rerun `pyworkon app install` after pyworkon/Ghostty upgrades; the original Ghostty app is never modified. `tests/test_app_cli.py` includes a real configuration/signature check when macOS and Ghostty are available; GUI launch/PID checks are separate from the normal test suite.
- `PyworkonContext` passed via Click's `obj`
- `Config.ai_agent_command` selects the command in the default tmux AI pane (default: `opencode`), including shell-quoted options and arguments. `TmuxManager.create_session()` passes shell-quoted `PYWORKON_TMUX_AI_AGENT_COMMAND` and `PYWORKON_TMUX_AI_AGENT_TITLE` to tmuxp because tmuxp expands variables before the pane shell parses them. These internal variables are separate from the raw `PYWORKON_AI_AGENT_COMMAND` configuration source. The title is the executable's basename. Project-local `.tmuxp.yml` overrides remain unchanged. Restart the daemon for configuration changes; existing sessions are unaffected.
- **`interfaces/shell/commands/__init__.py` shadows submodule names**: it does `from .agent import agent` (etc.), so `pyworkon.interfaces.shell.commands.agent` resolves to the Click *command* object, not the submodule, once the package is imported. Tests that need the submodule itself (e.g. `tests/test_agent_cli.py`) must use `importlib.import_module("pyworkon.interfaces.shell.commands.agent")` instead of `from ... import agent` / `import ...agent as x`.

### Agent Name Resolution (`pyworkon agent`)

`_resolve_agent_name()` in `interfaces/shell/commands/agent.py` derives a human-readable agent name instead of a bare PID:

1. `_find_agent_process()` — Claude Code, Codex, and OpenCode hooks can run via a transient shell, so the hook's direct parent (`os.getppid()`) may not be the stable agent process. Walks up the process tree (via `ps`) to find a `claude`, `codex`, or `opencode` ancestor, bounded to a few hops, falling back to the direct parent PID. `agent --pid` overrides this identity for integrations; tmux lookups target `TMUX_PANE` when present rather than the ambient active session.
2. For Claude Code, `_process_cwd()` resolves the `claude` process's cwd (`/proc/<pid>/cwd` on Linux, `lsof -a -d cwd -p <pid>` on macOS).
3. `_find_active_transcript()` — Claude Code transcripts live at `~/.claude/projects/<cwd-with-slashes-as-dashes>/<session-id>.jsonl`. A running session can silently move to a **new session ID** (e.g. after compaction) without the process's command line changing, so parsing `--resume <uuid>` from argv is unreliable — instead, pick the most recently *modified* `.jsonl` in that project directory, which reflects the session the process is actually writing to right now.
4. `_extract_latest_transcript_field()` — Claude Code writes live `{"type": "agent-name", "agentName": "..."}` entries to the transcript (the same short slug shown by dashboard/FleetView-style UIs — it can change mid-session as delegated sub-agents run) and a stable `{"type": "ai-title", "aiTitle": "..."}` entry. Use the **latest** `agent-name` entry, falling back to the latest `ai-title` entry.

Falls back to `<agent>-<pid>` whenever no Claude transcript name is available. Codex and standalone OpenCode CLI calls use this fallback name. Do NOT synthesize a title from the first user message — Claude Code already provides both fields above, use them instead of re-deriving.

### OpenCode V2 Integration

`pyworkon/assets/opencode/` contains the CLI-only TypeScript plugin. The wheel bundles its runtime files (`tui.ts`, `status.ts`), excluding development dependencies, tests, and tooling metadata. `pyworkon agentic opencode install` (`interfaces/shell/commands/agentic.py`) reads these package resources and copies the runtime files to `~/.config/opencode/plugins/pyworkon/`, respecting `XDG_CONFIG_HOME`. The former top-level `opencode` group has been replaced by the `agentic` group. OpenCode discovers the plugin directory automatically; no development checkout or configuration edits are needed. Rerun the installer after upgrading pyworkon to refresh the copied plugin.

The plugin must not run in the shared background server: only the CLI has a reliable `TMUX`/`TMUX_PANE` and terminal PID. It invokes `pyworkon agent --pid <terminal-pid> --name <session-title> --status <status>` with literal subprocess arguments (never a shell), targeting the existing daemon protocol without changes to the TUI or relay.

`status.ts` derives status from the selected root session and its family: pending permissions/forms take precedence (`waiting`), then execution (`working`), otherwise `idle`. A Solid reactive effect watches route, title, and cached state changes. OpenCode owns permission/form hydration; the plugin only reads its reactive cache and must not initiate synchronization. New sessions are cached optimistically before server creation, so even a cached session can return 404 if synchronized too early. Regression tests use OpenCode's actual data layer with a blocked creation request. Unrelated sessions/background tabs are excluded. `AgentReporter` serializes and deduplicates writes, reports failures once per outage, and clears only after in-flight writes finish during cleanup. `tui.ts` also performs bounded best-effort synchronous cleanup on process exit, since the exit event cannot await promises. Forced kills cannot run cleanup.

Runtime Solid imports must stay in `tui.ts`, where OpenCode resolves them to its shared runtime. Pass `createEffect` and `createRoot` into `watchAgent`; `status.ts` uses only type imports from `solid-js`. Importing Solid at runtime from the helper fails in the compiled OpenCode executable even when ordinary Bun tests pass. `loading.test.ts` tests the installed files against a compiled host without local `node_modules`, including host-signal reactivity and cleanup (ad-hoc signing the temporary host on macOS).

Run `make opencode-check` for frozen Bun dependency installation, strict TypeScript checking (including dependencies), and Bun tests. This is separate from `make test` (which covers lint/format-check/typecheck/pytest for the Python side only); Bun is a development requirement, not a Python runtime dependency.

`pyworkon/assets/skills/<skill-name>/SKILL.md` contains portable skills included in the wheel. The bundled `pyworkon-workspace` skill explains the provider/owner/repo workspace layout and targeted repository lookup. `pyworkon agentic skills-install` discovers all direct skill directories with a `SKILL.md` and recursively copies their complete contents using `importlib.resources` (including ZIP-backed resources). ## Nerd Font Icons

Icons are defined in `pyworkon/icons.py` — a dependency-free, top-level leaf module, **not** under any `interfaces/*` subpackage. `interfaces/tui/icons.py` and `interfaces/relay/icons.py` are thin re-export shims over it (see `pyworkon/icons.py`'s own module docstring for why: the relay and strip both need these constants and must not depend on the TUI package, which is expected to go away eventually, to get at them). **ALWAYS use explicit Unicode escapes** (e.g., `""`) — never paste the raw glyph character. Raw glyphs get silently stripped by formatters and editors, producing empty strings that are hard to debug.

```python
# GOOD
ICON_GITHUB = ""  # (nf-fa-github)

# BAD — glyph will be silently stripped
ICON_GITHUB = ""  # (nf-fa-github)
```

**This stripping risk is not just a typing mistake — it happens when *relocating* icon-bearing code too, including through an agent's own read/regenerate cycle.** When `pyworkon/icons.py` was split out of `interfaces/tui/icons.py`, retyping the file's content (reading it, then writing a new file with what looked like the same text) silently dropped every raw glyph down to an empty string — confirmed the hard way, caught only once a test asserting glyph length failed and the user reported empty icons in the running app. The fix: when moving/copying a file (or section of one) that contains raw PUA glyphs, get the exact bytes via `git show <ref>:<path>` (or a plain filesystem copy) and splice new surrounding content around that untouched byte-exact block — never let the glyph-bearing lines pass through a manual retype, even an apparently faithful one.

**ONLY use single-width icons** from the BMP Private Use Area (U+E000–U+F8FF): Powerline, Devicons, Font Awesome, Codicons, etc. **NEVER use Material Design Icons** (U+F0000+, Supplementary PUA) — Nerd Fonts v3 renders them as double-width, which breaks Textual's layout calculations.

### Agent Status Icons

Agent status is set via CLI hooks as plain strings (`idle`, `working`, `waiting`). The TUI maps these to colored Nerd Font icons via `_AGENT_STATUS_ICONS` in `widgets/agent_list.py`. Unknown status values are rendered as-is.

### Reuse in the relay web dashboard and the strip

`pyworkon.icons.DASHBOARD_ICONS` is built directly from the constants in that same module (not from the TUI) and is reused as-is by both `interfaces/relay/icons.py` (re-exported for the relay dashboard) and `interfaces/strip/app.py` (imported directly — the strip must not import from `interfaces/relay` at all, see the "Strip" section's `static/picker.html` notes). Add new dashboard/strip icons to `pyworkon/icons.py`, not as hardcoded glyphs in `dashboard.html`/`strip.html`/`picker.html`.

## Key Patterns

- **No inline imports.** All imports go at the top of the file, using Python 3.15's `lazy import X` / `lazy from X import Y` (PEP 810-style soft keyword) instead of moving an import into a function body to defer its cost. Never use a plain `from X import Y` inside a function or method — the one narrow exception is an import kept purely for its top-level *side effect* (e.g. `pyworkon/interfaces/__init__.py`'s `from .shell import commands`, which registers CLI subcommands) where the imported name is never actually accessed by name: a `lazy` binding only resolves on access, so a name that's deliberately never touched would never load at all if made lazy — that one must stay eager and inline.
  - Eager (plain `import`/`from`): names needed immediately at module-load time — base classes, decorators, module-level dict/constant literals, pydantic/dataclass field *types* (pydantic's metaclass resolves field annotations during class-body evaluation, forcing immediate resolution of a lazy binding, so lazy would be a silent no-op there), and anything reachable from a module-level singleton's `__init__` (e.g. `config.py`'s `config = Config()`, `project_mgr.py`'s `project_manager = ProjectManager()`).
  - `lazy import X` / `lazy from X import Y`: names used only inside function/method bodies as genuine runtime values (instantiated, called, isinstance-checked). Ruff's `TID255` (`lazy-import-immediately-resolved`) catches *some* misuses, but not ones reached indirectly through a metaclass or a module-level singleton's call chain — when unsure, verify empirically (`import sys; baseline = set(sys.modules); import the_module; set(sys.modules) - baseline`) rather than trusting ruff/mypy alone.
  - `if TYPE_CHECKING:`: names used only as type annotations, never as a runtime value (zero import cost, unchanged from before this convention existed).
- `contextlib.suppress(Exception)` for best-effort DOM queries in watchers
- `contextlib.suppress(subprocess.CalledProcessError)` for optional tmux/git calls
- `StrEnum` for all enum types (`PRStatus`, `PRState`, `ProviderType`, `CommandType`, `ResponseType`)
- Pydantic models for API-facing data, `@dataclass` for internal transfer objects
- `appdirs` for platform-specific config/cache paths
- `diskcache.Cache` for project list persistence
